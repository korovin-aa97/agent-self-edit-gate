# Agent Self-Edit Gate — Agent Bootstrap

Last updated: 2026-08-29. Repository status: **v0.1.0 public-release candidate**.

Read this file first, then `README.md`, `selfedit-policy.example.toml`, the
current source, and `docs/PUBLIC_RELEASE_PLAN.md` before changing anything.

## Product in one sentence

Agent Self-Edit Gate lets a coding agent improve its prompts, skills, and agent
definitions without letting it rewrite the files that grant permissions or
disable enforcement.

## Positioning

The product is a narrow runtime self-edit gateway. It is not a general agent
firewall, sandbox, package manager, or enterprise governance platform. Describe
it as the layer between "the agent wants to edit its own behaviour" and "the
repository accepts that edit under policy".

Do not use the generic slogan "firewall for AI agents". That category is
already occupied and implies protections this tool cannot provide.

## Current state

- Version `0.1.0`, packaged under Apache-2.0.
- The CLI supports bounded checks, exact replacement, whole-file writes,
  atomic replacement, deterministic JSON errors, and receipt verification.
- Policy and receipt schemas are versioned at v1.
- Generic, Claude Code, and Codex profiles are data files, not engine branches.
- Hostile tests cover traversal, symlinks, overlap, binary/extension/size
  limits, races, audit failures, crashes, stale intents, policy swaps, and
  receipt truncation.
- The README and threat model explicitly state that this is not a security
  boundary while an agent can write around the CLI.

## Non-negotiable boundaries

- Never claim the CLI alone prevents shell, direct filesystem, IDE, or tool
  writes. Enforcement requires an external trust boundary that makes the gate
  the only allowed writer.
- Immutable/protected rules win over mutable rules, always.
- Refuse traversal, symlinks, ambiguous replacement anchors, oversized writes,
  unsupported extensions, and receipt failures.
- A receipt generated by the same unrestricted agent is not independent proof.
  Explain the need for protected CI, sandbox policy, or another external anchor.
- No telemetry, network service, hosted control plane, or fleet orchestration in
  the open-source core.
- Keep the extraction clean-room: no customer data, internal hostnames, private
  branch names, incident IDs, credentials, or proprietary fleet topology.

## Working rules for future agents

- Use Python 3.12+ and type every public interface.
- Prefer standard library dependencies unless a dependency materially improves
  security and has been reviewed.
- Make policy decisions deterministic; an LLM must never decide whether a path
  is protected.
- Every behaviour change needs a regression test and changelog entry.
- Preserve backwards compatibility of policy and receipt formats after v0.1.
- Separate exact facts from marketing claims and cite dated evidence for any
  competitor comparison.
- Before a public launch, repeat name and competitor checks using direct GitHub,
  package-index, and website access; do not rely only on search indexes.

## Release authority

Agents may prepare code, documentation, assets, workflows, drafts, and dry-run
evidence. Changing repository visibility, publishing a package, creating a
public release, submitting to a directory, or posting launch content requires
an explicit instruction from the repository owner in that session.
